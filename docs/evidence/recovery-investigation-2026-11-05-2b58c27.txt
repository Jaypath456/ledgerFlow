How recovery_s is measured (chaos/lib.sh probe_recovery)
  From the end of the fault, POST a probe payment with curl -m 5 and poll it to COMPLETED; retry every 0.5 s. k6 runs 60 s and the fault
  fires at t = 15 s. When payment-service queues requests for longer than 5 s, every probe POST times out until the load stops, so
  recovery_s cannot be shorter than the load time left after the fault (the load runs 60 s; the fault starts at 15 s), whatever the fault is.

Cause
  PaymentSecurity encodes every configured identity with PasswordEncoderFactories.createDelegatingPasswordEncoder(): stored
  {bcrypt}$2a$10$..., cost 10 (BCryptPasswordEncoder default strength, spring-security-crypto 7.1.1). The API is stateless HTTP Basic, so
  each request runs one bcrypt verification at cost 10. Verification cost follows the stored hash (BCrypt.checkpw). Supplying pre-hashed
  {bcrypt} values through config is not possible: the configured value is always encoded again as a plain password.
  DaoAuthenticationProvider (spring-security-core 7.1.1) also re-hashes a stored password after login when the verifying encoder's
  upgradeEncoding() is true (stored cost < encoder strength), so the strength has to be set on the PasswordEncoder bean, not only on the
  encoding side.

Conclusion
  Confirmed: per-request bcrypt verification at cost 10 saturates payment-service CPU at 100 requests/s on this host. Requests queue for
  seconds, the probe's 5 s POST cannot get through until the load stops, and recovery_s reads 40.8-48.7 s in 7 of 9 runs whatever the fault. Lowering only
  the load identities' cost to 4 brings hot-account, pause-postgres and restart-kafka within the targets (<= 5, <= 5, <= 20 s). Replay
  (14.2 s, single run, run 1 on fresh topics) stayed above the <= 10 s target in this experiment; see the Phase 1b final campaigns.
  Not tested separately (not needed to explain the plateau): k6 --memory 1g, postgres 1 GiB limit, velocity guard row, JVM heap.
  Locally grafana/k6:latest and grafana/k6:2.3.0 are the same image ID (0c6e79b98aff), and postgres:17 and postgres:17.11 are the same
  image ID (bbdfc26f27f4); which image digests the 2026-10-25 campaign used is not recorded.

Aborted run (B, first attempt, chaos/results/chaos-20261105-152401, not counted)
  Run 1 (replay) k6: accepted=4293 failed=1101 retries=6329 rate=89.9/s post_p50=23.1ms. The broker's group coordinator then failed:
  "ERROR [group-coordinator-event-processor-0]: Failed to run event InternalEvent(name=FlushBatch)": java.lang.ArrayIndexOutOfBoundsException
  "Histogram recorded value cannot be negative" in CoordinatorRuntimeMetricsImpl.recordEventQueueTime (apache/kafka:4.0.0). After that,
  offset commits failed with "The coordinator is not available", the payment-service group kept a lag of 1064-1096 per partition, and the
  runner's replay wait (until consumer lag = 0, no timeout) hung. The stack was taken down. Probable trigger: a negative queue time from a
  clock step in the Docker VM; not verified against Kafka's issue tracker. chaos/run_chaos.sh now fails a replay run whose lag does not
  drain in 300 s instead of waiting forever.
