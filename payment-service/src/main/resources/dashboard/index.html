    How a payment moves

    Idempotency

    The idempotency key is the first row written. A second request with the same key waits on that row's primary key, then returns the stored original response byte for byte. Same key with a different body → 422. One key can never create two payments.

    Transactional outbox

    The payment and its PaymentRequested event are committed together. A relay publishes the event afterwards and marks it only after Kafka acknowledges. A crash can cause a re-send, never a lost event.

    Idempotent consumers

    Kafka delivers at least once. Each consumer records the event id in processed_events in the same transaction as its effect, so a redelivered event changes nothing.

    No overdraft under contention

    The ledger locks both accounts with SELECT … FOR UPDATE in ascending id order (no deadlocks), checks funds under the lock, and writes balanced debit/credit entries. A DB CHECK backs it up.

    Recovery

    A payment still PENDING_LEDGER after 30 s is re-requested with a fresh event id. If the ledger already decided, it re-sends the stored result instead of posting again, so the payment converges and money moves once.

    Invariants

    • I1 every ledger transaction and the whole ledger sum to zero
    • I2 a payment is posted at most once
    • I3 accepted payments reach a terminal state after recovery
    • I4 non-SYSTEM balances are never negative
    • I5 cached balances equal the sum of ledger entries
    • I6 idempotency records are consistent with their payments

    Each service can only read its own schema, so the dashboard shows each service's checks. Checks that need both schemas (e.g. COMPLETED ⇔ posted) are verified per scenario for the scenario's payments, and for the whole database by ./demo/run.sh invariants, which runs chaos/verify_invariants.sql as the database superuser.
