    How LedgerFlow works

    1. Payment
    2. Payment Service saves it and queues a message
    3. Kafka delivers the message
    4. Ledger Service moves the money, exactly once
    5. Completed / Failed

    LedgerFlow prevents duplicate financial effects, overdrafts and inconsistent balances, even when requests are retried or processed concurrently.

    View technical details
    • Idempotency: each request ID is stored first; a repeat returns the stored original response, and the same ID with a different body is refused (422).
    • Transactional outbox: the payment and its PaymentRequested event are saved in one database transaction, then published to Kafka. Nothing is lost if a service crashes.
    • Idempotent consumers: every event id is recorded with its effect, so a redelivered message changes nothing.
    • No overdraft: the ledger locks both accounts in a fixed order, checks funds under the lock and writes balanced debit/credit entries (LedgerPosted / LedgerRejected).
    • Recovery: a payment still processing after 30 s is asked about again; the ledger replays its recorded decision instead of moving money twice.
    • Invariants I1–I6: ledger sums to zero · posted at most once · accepted payments finish · no negative balances · balances match entries · request IDs consistent.

    Deployment

    • Deployment modeLocal single-instance demo
    • High availabilityNot configured
    • Recovery / correctnessVerified

    LedgerFlow's local demo intentionally runs one instance of each part (one database, one Kafka broker, one of each service). It demonstrates safe recovery and financial correctness under temporary failure, not zero-downtime high availability: if a part is down, payments wait, and nothing is lost or doubled when it comes back.
